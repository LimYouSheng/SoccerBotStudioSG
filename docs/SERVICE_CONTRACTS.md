### Mutation testing and state-changing API tests

Code mutation testing deliberately changes one critical behavior in an isolated disposable checkout to establish whether the intended test detects it. Include representative mutants that remove a fresh write-boundary check, permit cross-account scope, bypass consent/price/capacity/lead validation, admit a duplicate booking/payment effect, trigger a post-hold slot query, weaken signature verification or allow confirmation without paid evidence. For each mutant record source revision, operator/change, targeted invariant/test, baseline pass, mutant failure and restoration. An invalid or non-compiling mutant is not evidence that a business invariant is tested. Investigate surviving non-equivalent mutants; report uncovered, equivalent and untested cases explicitly. Never lower assertions, skips, retries or timeout gates to obtain a result. No mutation tooling, coverage percentage or completed campaign is claimed by this documentation; select a bounded implementation and review any coverage target before execution. Do not publish or deploy mutant code.

State-changing API tests are distinct from code mutation testing. In isolated application/runtime tests, exercise concurrent/duplicate submissions, repeated/out-of-order authenticated callbacks, interruption after an uncertain provider write, expired authorization/deadlines and recovery claims. Assert durable attempt ownership, retained unknown-write evidence, no duplicate effects, no deadline extension and no automatic replay after ambiguity. Live provider writes, payments, refunds or cancellations are permitted only by the separate owner-approved acceptance packet; a mutation-test requirement grants no such authority.

### Latency and performance evidence

Measure the customer journey, not just endpoint or provider-call counts. Capture at least Details → Review (including hold creation), Continue to payment → hosted handoff, and payment return → verified confirmation. Break down browser queueing/network, account-coordinator wait, catalogue/identity/availability reads, preparation/preflight, holding creation/readback, payment request and recovery/confirmation. Preserve request correlation and original attempt identity while excluding contact, cookies, keys and capability URLs from shared evidence.

Record exact deployed source/version, target company/environment, device/browser/network, time in SGT, test case, visible/background calendar work, cold versus warm caches, request/provider-call counts, errors and observed durations. Compare baseline and candidate under comparable conditions; distinguish browser-aborted work from server work that finishes. Deterministic queued-calendar tests prove ordering/serialization, not live speed. A faster endpoint cannot pass if validation or effect correctness regresses.

Report individual observations and sample size for the first bounded owner trial. Report medians/tail percentiles only with an adequate declared sample and sampling method; never infer p95 or a repeatability claim from one booking. Agree latency acceptance thresholds and additional booking/call/load budgets before a benchmark campaign; do not invent a target, multiply real payments for statistics or overload shared studio/provider quotas. Historical approximately53-second Details → Review evidence is an old-account observation, not a current baseline or target. Fewer calls, a warm cache or passing CI cannot establish measured new-account latency improvement.
