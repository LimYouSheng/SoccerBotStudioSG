## M3.5 implementation design — 10 October 2026

Status: design fixed before implementation and now implemented in source with focused synthetic checks; final CI and live/device acceptance remain pending. Existing identity/access owners remain authoritative. Remember me is explicit, default off. A fresh consumed email challenge may create one digest-only remembered family with account/origin, verified email, original verification time, fixed expiry at exactly 90 days, current/previous token digests, rotation time and revocation time. A separate access-to-family link associates short verified sessions; no provider profiles, booking records or raw tokens are copied.

- The persistent `__Host-soccerbot-remember` cookie is Secure, HttpOnly, SameSite=Strict, Path=/, with Expires equal to the original server expiry. Cookie expiry is advisory; every restoration checks primary durable state. No raw token reaches JSON, storage or logs.
- POST `/api/identity/restore` requires exact HTTPS origin and an existing valid short guest capability. It restores only identity into that guest's own new context, with expiry bounded by both guest expiry and the original family expiry. It never returns an old guest capability, owner or attempt. GET identity is read-only. Missing remembered credentials return no identity; invalid, revoked, expired or foreign credentials fail closed.
- Rotation uses an atomic current-digest compare-and-set. A server HMAC derives the single successor from the presented token; concurrent users of the previous digest receive that same successor only within 30 seconds. A successor is not rotated again during that interval. Previous-token reuse at/after the grace end revokes the family; unrecognized older tokens are denied. No rotation changes original verification or expiry. A lost response can recover only within this grace; otherwise verification is required, with no guessed retry or plaintext token storage.
- Device sign-out revokes the guest and every family linked to its identity, including a newly issued family whose response is delayed. Durable triggers revoke related short identity sessions and guest access while retaining attempts/recovery rows. Late cookies can remain in the browser but cannot restore revoked authority. Delayed responses may require verification again; they must never reveal another subject.
- All-device sign-out requires a currently valid short identity freshly established by email verification within five minutes, not restoration. It atomically records a subject revocation cutoff, revokes the subject's families and short sessions, and prevents challenges created before that cutoff from establishing new authority. A missing/expired/failing authorization performs no subject-wide write. Future challenges require a new email verification.
- The frontend invalidates cached identity before authentication transitions and correlates every completion to its current operation. It re-reads server identity after verification/restoration. Profile lookup remains unavailable pending M2.5/M3.6; customer-entered booking corrections cannot update provider profiles.

Additive migration0013 must preserve every applied0001–0012 byte and every prior table row. Deployment/migration are unapproved. A future finite live packet must explicitly revoke every newly issued remembered family and verify restored-access denial during closure; disabling delivery alone does not revoke a remembered credential. Failure rolls back the batch and produces unavailable; no cookie is issued before durable success. Rollback is a closed application release retaining the additive schema and revocation data, never dropping tables or restoring expired credentials. Retention/scheduler activation requires a separate reviewed packet.

Its in-memory key includes mode/adapter lifetime, sorted unique dates, player count, guest/member and account-email context, attempt ID/status, Singapore clock minute and current demo session identity/expiry. Selection/contact edits that do not change those inputs reuse the shared read; changed dates, players, account/session, attempt outcome, focus/minute refresh or explicit retry invalidate it. A known checkout/payment/status conflict advances the query revision and re-reads availability before continuation; it does not replay the failed action. No persistent availability cache or live latency claim. Displayed availability is not a reservation; checkout independently revalidates.

Query results for replaced revisions or disposed subscriptions are discarded; AbortSignal releases supported work, while a correlation check remains mandatory. The service boundary ends the caller wait even if an adapter ignores abort. A just-selected date stays loading until that date was actually queried. Failure/unavailable/unknown is never rendered as an empty day; the basket retains entries and blocks Continue until validated. Explicit retry re-reads without clearing entered information; no automatic request retry.

Checkout/pay/check/resolve use one synchronous in-flight guard and an immutable captured draft/attempt revision. Action state also belongs to its adapter instance; replacing that adapter cancels old work and releases the new screen from obsolete loading. Success commits only while the owner is mounted, the request is current and the demo member session still matches. Editing during checkout aborts/discards it; payment/status actions block alternate draft writes. Leaving Review or Payment cancels that screen's pending wait. Interrupted status resolution keeps the original checking attempt and offers an explicit status check; cancellation cannot undo an already dispatched effect. Existing provider-side unknown-write recovery remains separate and unchanged. Live writes stay unavailable, so this UI guard is not represented as production idempotency.

Review waits for validated checkout before navigating. Payment exposes pending action state and safe failures; duplicate clicks cannot create another logical action. Error/cancellation preserves drafts and attempt identity. Browser reload resumes the existing demo checking deadline; only demo mode loads/saves demo storage. Preview disclosures, navigation, layout, identity behavior and the protected confirmation page remain intact.

### Attempt state and durable recovery requirements

1. Before external mutation, atomically create/claim a journal record with customer/guest capability binding, request hash, originating environment, immutable approved draft and version.
