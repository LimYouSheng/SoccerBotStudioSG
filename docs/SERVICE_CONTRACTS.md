# SoccerBotStudio — Service Contracts

Canonical boundary reference, introduced 4 October 2026 under the latest OneFitfinity process. Rules & Architecture owns product/security invariants; Journey owns changes and evidence. This document describes the actual initial interface and labels future requirements. It does not create HTTP endpoints.

## Composition and authority

`src/services/index.ts` selects four demo adapters only. `src/services/contracts.ts` owns their TypeScript interfaces; `src/domain/booking.ts` and `contact.ts` own relevant runtime schemas. There is no production adapter, API client, Worker, provider SDK or mode flag. Booking and identity methods are synchronous browser operations; enquiry alone returns a Promise. Do not pretend these positional signatures already meet the future named asynchronous request contract.

Demo state is versioned, schema-checked browser storage. The booking provider in `src/features/booking/provider.tsx` orchestrates React state, draft persistence, route prerequisites and simulated payment timers. It is not a server authorization boundary. Synthetic identity may expire; its current-session check in provider checkout is UI orchestration, not production service security. Browser IDs, stored email and confirmation objects are untrusted for live operations.

Supporting boundaries: `src/services/storage.ts` parses versioned draft/attempt data. Version 2 writes use `soccerbot-next-demo-v2`; when absent, version 1 is upgraded without deleting the old source. The former global instructor is carried into each session; unassigned drafts derive it from the demo schedule. Existing attempt ID/status/deadline, booking reference/amount and studio allocation remain intact. Old receipt snapshots are upgraded when read so retry/resolve reuses the original paid receipt. Removed contact fields are stripped. The adapter tolerates unavailable/malformed browser storage; this can discard local state and must not be reused for durable live attempts. `exports.ts` builds ICS text and downloads PDF/calendar from a supplied confirmed demo snapshot; download initiation does not prove readable bytes, device save or external delivery. Production confirmation must be fetched through an authorized capability first.

## Demo instructor rotation and customer disclosure

`demoSession(slot)` in the single demo schedule owner returns a `Session` with its starting-block instructor and optional rotation boundary, or null for invalid starts. Blocks start at 09:00, 12:00, 15:00 and 18:00. `availability(date)` returns 14 positions from 09:00 through 19:50, each carrying that assignment and a shared-studio availability flag. Unavailable slots are not selectable. A 20:40 start cannot fit before closing and is absent. The former common-instructor intersection operation is removed: sessions from different blocks or dates can share one booking.

Optional `rotationAt` is the boundary crossed strictly before session end: `12:00` at 11:30 and `15:00` at 14:50. It does not change the booked instructor; the starting instructor stays throughout. The time card and shared session renderer disclose this before payment and on confirmation. Ending exactly at 18:00 produces no crossing notice. Checkout re-derives each session assignment and rejects a forged/stale instructor or missing/incorrect rotation disclosure. It accepts valid mixed-instructor sets and still rejects overlaps/capacity conflicts. Display metadata confers no authority. Elapsed slots today remain the documented M4.1 limitation; no live staffing or provider integration is claimed.

## Current data and state model

- `Slot`: date plus local start time; no provider booking ID.
- `Session`: date/start plus required assigned `instructor` and optional `rotationAt`; these values persist through draft, payment, confirmation and exports.
- `BookingDraft`: guest/member mode, account email, 1–4 players, up to 100 selected sessions, contact and policy acknowledgement. No booking-level instructor remains. The 100-slot limit is a current schema bound, not approved live cart size.
- `ContactDetails`: full name, email, phone, preferred contact method and optional academy/school/organisation. Removed participant/guardian/emergency/requirements/notes fields are stripped by schema parsing and are no longer required by validation.
- `Attempt`: ID, reviewed draft, status, selected demo outcome, checking deadline, optional booking. Status set: `ready`, `checking`, `declined`, `pending`, `late`, `paid`.
- `Booking`: reference, creation timestamp, frozen draft, studio-assigned sessions and total cents. It has no SimplyBook/SBPay/HitPay invoice association yet.
- Checking/pending/late/paid lock draft/payment mutation. Decline is retryable. Late displays help without another payment. Paid leads to confirmation. Draft edits clear acceptance and the earlier unlocked attempt.
- Missing live states include explicit expired/unknown/partial failure/cleanup-required distinctions. Existing demo late/pending labels must not be used to hide those outcomes.

### Shared envelope and authority

Requests use named records with opaque `requestId`, bounded operation-specific inputs and, for mutable customer state, `cartRevision` or `attemptVersion`. Server configuration derives account/environment/provider mappings; the browser cannot choose credentials, prices, authorisation or a raw provider method. A public service/instructor identifier is validated against the allowed logical catalogue. Capability/session comes from protected transport, not an email/role in the body. Request IDs are correlation only, not authority or a substitute for an idempotency key.

Successful read results include `requestId`, normalized query/revision, `configVersion`, server `observedAt` and `expiresAt`, freshness state and minimal allowed data. An opaque snapshot ID identifies display evidence only; do not call it a provider revision/hold unless the provider proves those semantics. Preserve original observation age across cache layers. For time-sensitive UI use server-relative freshness conservatively, accounting for round-trip/elapsed time; never trust the customer's clock to authorize a booking. Checkout always uses trusted server time.

Closed failure categories: invalid request; unauthenticated/forbidden; unsupported capability; stale selection/configuration; slot conflict; provider throttle; quota exhausted; temporarily unavailable; deadline exceeded; unknown write outcome; partial completion; cleanup required. Freeze exact code names at M3.2. Return safe user-action/retry guidance, correlation, and retry-after only where meaningful. Preserve internal HTTP/JSON-RPC error classification without leaking payloads. An empty successful matrix, malformed response and upstream error are different outcomes. A timeout after dispatch is never reported as a definite rejected booking.

Backend-only provider transport accepts a closed supported operation descriptor, deadline, priority and declared retry class. It uses the one account governor for every physical call. The adapter parses results; the orchestrator decides whether a write is known accepted, rejected or unknown. Auth refresh cannot silently replay a mutation whose commit status is uncertain. Read sharing keys include operation parameters, account/environment/config generation and required freshness barrier; never share customer records across principals or treat all reads as public.

### Attempt state and durable recovery requirements

1. Before external mutation, atomically create/claim a journal record with customer/guest capability binding, request hash, originating environment, immutable approved draft and version. Enforce uniqueness of the idempotency key in its principal scope. A new key cannot bypass an unresolved overlapping attempt for that same customer/draft without reconciliation. This reduces duplicate intent; provider capacity remains the final cross-customer guard.
2. Record each intended external write and dispatch state before sending. Track not-dispatched, dispatched/unknown, accepted or rejected separately from customer-facing stage. Persist returned provider IDs and any supported reconciliation correlation. Never invent provider idempotency or exactly-once guarantees. If an unreturned booking cannot be identified reliably, stop automatic replay and retain manual recovery as an explicit blocker.
3. Intended workflow distinguishes creating, partial/unknown, checkout-ready, awaiting payment, paid, declined, expired, late and cleanup-required. Freeze exact transitions in M2.5 with evidence. Store provider-observed state plus financial associations; a later-arriving weaker observation must not regress verified paid evidence. Reconcile contradictory newer evidence explicitly.
4. All accepted sessions must belong to the intended account/environment/resource/customer association and matched invoice/currency/amount before returning a checkout URL. Bind any quoted amount/version to the exact cart and reject/re-present changed pricing. A batch identifier alone proves neither atomic acceptance nor a single payable invoice.
5. On partial failure, do not offer payment. Cleanup requires a current positive unpaid determination and applies only to this attempt's newly accepted records. Check races with settlement before cancellation; unresolved cancellation/payment becomes cleanup-required. Cancellation and refund remain distinct, and refunds are native-authorized staff actions.
6. Foreground disconnect/deadline does not delete the attempt or release assumed provider capacity. Durable due time, lease owner, expiry and version let one recovery worker resume after process loss. The scheduler may use the selected coordinator alarm mechanism, but the D1 journal is authoritative; prove wakeup/restart/lease recovery before live writes. A retry never generates an unrelated new attempt for an unknown outcome.
7. Invalidation generation changes bracket writes and reject stale in-flight cache fills. Affected unknown ranges remain under recheck. Different selected dates must all be invalidated. Native-admin bookings remain outside our lock and must be caught by provider authority/freshness, never by a copied local schedule.

### Transport, privacy and contract acceptance

- Live auth, rate limits, admission, freshness and state checks apply equally to initial load, edit, checkout, callback, status, retry and recovery. Frontend disabled buttons are UX, not enforcement.
- Protected results and tokens never enter shared caches or public logs. Minimize returned instructor/client fields, set protected responses to `no-store`, and use named capability scopes. Background prefetch is read-only and never sends customer data to public cache keys.
- Contract fixtures must cover same-key/different-body submissions, reordered replies, wrong account/config/cache key, stale timestamps, expired capability, split-brain attempt claims, coordinator restart, token-refresh stampede, throttle-as-HTTP-200, lost response after provider commit, incomplete multi-session acceptance and duplicate/out-of-order/absent callback. Test-cache bypasses still obey the governor.
- Provider proof and deterministic doubles have different receipts. No exact endpoint mapping, final live cart limit, callback authentication scheme or payment detection guarantee is accepted until M2.5 records the actual supported route. Update this catalogue in place when implemented; do not create competing latency-specific service adapters or documentation owners.

### End-time result interpretation

- R2 selected 36 cases, with 21 generated cases explicitly omitted under the request budget. Both availability snapshots contained the same 268 starts. All 16 selected starts offered in both snapshots returned 50-minute intervals.
- Ten starts absent from both snapshots still returned an end datetime. Caelan on 19 October: 12:20, 13:10 and 13:40 all returned 14:50 despite being absent; his offered 14:00 returned 14:50. These observations do not turn the service into a 150/100/70-minute session. The calculator's internal mechanism remains unproved.
- Ten other absent starts returned `null` with successful transport/RPC envelopes. Keep null as unresolved; do not coerce it to false, zero, an empty schedule or availability. The documented negative `false` is distinct; it was not observed in this R2 sample. Unknown shapes fail validation.
- Catalogue duration 40, the supplied settings screenshot's 10-minute buffer after, and sampled 50-minute provider intervals are consistent with 40+10. The end result is not independently labelled customer play duration, and read-only evidence does not prove buffer enforcement under competing bookings.
- Display play end as start +40 and changeover end as start +50 under the approved rule, clearly keeping those derived values distinct from provider-returned fields. Preserve full staffing during play and studio protection across instructors. Require exact fresh matrix membership plus the provider's final booking acceptance.
